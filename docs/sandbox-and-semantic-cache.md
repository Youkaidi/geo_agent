# Geo-Agent 沙箱与语义缓存功能设计说明

## 1. 文档目的

本文从业务视角说明 Geo-Agent 第一版沙箱和语义缓存的设计，包括：

- 为什么需要这两个能力；
- 它们在 Agent 总体链路中的位置；
- 当前版本的执行流程和技术方案；
- 故障时如何降级，以及哪些边界尚未覆盖；
- 后续从单机原型演进到企业级平台的建议。

这两个能力解决的是不同问题：

| 能力 | 核心问题 | 业务价值 |
| --- | --- | --- |
| 工具执行沙箱 | Agent 生成或选择的训练命令能否安全执行 | 限制误操作和恶意操作的影响范围，保护主机、数据、凭证和 GPU 资源 |
| 语义缓存 | 相似问题是否需要再次调用大模型 | 降低模型费用和响应延迟，同时控制错误复用、数据串用和答案过期风险 |

异步任务队列、沙箱和语义缓存并不是相互替代的组件：任务队列负责长任务可靠运行，沙箱负责执行安全，语义缓存负责模型调用效率。

## 2. 总体架构与业务流程

```text
用户
  │
  ▼
Geo-Agent CLI / Pi AgentSession
  │
  ├─ 知识问答 ─► 语义缓存策略门
  │                ├─ active 命中 ─► 返回缓存答案，并写回会话历史
  │                ├─ shadow 命中 ─► 只记录指标，仍调用模型
  │                └─ 未命中/绕过 ─► 调用模型 ─► 合格答案写入缓存
  │
  └─ 实验操作 ─► Pi 地质领域工具 ─► 持久化任务队列
                                      │
                                      ▼
                                    Worker
                                      │
                                      ▼
                              沙箱策略与执行边界
                                      │
                                      ▼
                         Python / PyTorch / 单机 GPU
                                      │
                                      ▼
                        检查点、日志、指标、产物和通知
```

这里有两个关键边界：

1. **有副作用的实验请求不进入语义缓存。** 提交训练、取消任务、查询实时状态、读取 GPU 状态等请求必须读取当前真实状态，不能复用历史答案。
2. **训练程序只能由 Worker 在沙箱边界内启动。** 主 Agent 只调用受控的领域工具，不直接获得任意 Shell 执行能力。

## 3. 工具执行沙箱

### 3.1 业务背景

Geo-Agent 最终会替用户运行训练代码。与普通问答不同，这类操作会访问本地文件、占用 GPU、启动子进程，甚至持续数小时。如果没有边界控制，一次模型误判、提示词注入或项目配置错误都可能造成：

- 执行任意命令；
- 读取训练项目以外的隐私文件；
- 把 API Key 等宿主机凭证传入训练进程；
- 覆盖数据集、代码或其他实验产物；
- 无限占用 CPU、内存、GPU 或进程数；
- 任务超时后遗留孤儿进程或容器；
- 实验结果无法追溯到实际执行条件。

因此，沙箱的业务目标不是保证训练一定成功，而是把一次失败或越权执行的影响范围限定在当前实验内，并留下可审计记录。

### 3.2 当前执行流程

```text
Worker 领取任务
  │
  ├─ 校验 Python 解释器、训练项目、数据目录和输出目录
  ├─ 校验允许执行的模块和参数
  ├─ 生成受控环境变量
  ├─ 根据配置生成 process 或 Docker 执行计划
  ├─ 将执行计划写入任务检查点
  ├─ 启动训练并持续收集输出
  ├─ 正常完成 ─► 保存结果摘要与产物位置
  └─ 超时/失败 ─► 终止进程树或容器 ─► 进入重试或死信流程
```

将沙箱放在 Worker，而不是只放在主 Agent，原因是 Worker 才是产生操作系统副作用的最终位置。即使 Agent 层的提示词或工具参数被绕过，Worker 仍会进行独立校验。

### 3.3 当前两种模式

| 模式 | 适用阶段 | 已有保护 | 隔离强度 |
| --- | --- | --- | --- |
| `process` | 本地开发和第一版验收 | 命令白名单、路径边界、环境变量过滤、超时、进程树清理 | 较弱；进程仍共享宿主机内核和文件系统权限 |
| `docker` | 后续启用的正式实验环境 | 非 root、只读根文件系统、代码和数据只读挂载、输出目录可写、能力删除、资源限制、网络策略、超时清理 | 较强；需要 Docker、训练镜像和 GPU 容器运行时 |

当前默认使用 `process`。Docker 执行路径已实现，但本机尚未安装 Docker，因此不能把当前版本描述为已经具备容器级强隔离。

### 3.4 第一版安全策略

#### 命令白名单

- 只允许配置中指定的 Python 解释器；
- 当前训练入口固定为 `python -m ablation.run_ablation`；
- Agent 不能提交任意 Shell、PowerShell 或其他二进制命令。

这比对命令字符串做黑名单过滤更可靠，因为黑名单很难枚举所有转义、管道和子进程启动方式。

#### 文件系统边界

- 工作目录必须是配置的训练项目目录；
- 项目路径必须位于训练项目根目录内；
- 输出只能写入当前实验的运行目录；
- 数据只能来自配置的数据根目录或运行时合成数据目录；
- 所有路径在执行前都进行解析和越界检查。

Docker 模式进一步将代码和数据以只读方式挂载，只对当前实验输出目录授予写权限。

#### 凭证与环境隔离

Worker 不会把完整宿主机环境直接传给训练进程，只传递运行训练所需的受控变量，例如系统路径、临时目录、CUDA/NVIDIA、OMP/MKL 和 Python 编码配置。OpenAI Key、代理凭证及其他无关密钥默认不会进入训练环境。

#### 资源和生命周期控制

Docker 模式支持配置：

- CPU 数量；
- 内存上限；
- 最大进程数；
- GPU 设备；
- 网络模式；
- 只读根文件系统和临时目录；
- 非 root 用户；
- `no-new-privileges` 和删除 Linux capabilities。

两种模式都有最大运行时间。超时后，进程模式会终止完整进程树，Docker 模式会强制删除本次任务容器，避免后台残留继续消耗资源。

### 3.5 失败原则与审计

沙箱采用 **fail closed**：路径越界、命令不在白名单、Docker 不可用或镜像不存在时，任务在预检阶段失败，不会悄悄降级成不受控执行。

任务检查点会记录沙箱模式、执行计划、启动结果和最终状态。这样能够回答：

- 哪个实验使用了什么隔离模式；
- 哪些目录被挂载；
- 分配了多少资源；
- 任务因训练错误、超时还是策略拒绝而失败。

### 3.6 当前局限

- `process` 模式不是安全容器，无法抵御能够调用宿主机系统接口的恶意 Python 代码；
- Docker GPU 模式仍需安装 Docker、构建训练镜像，并验证 NVIDIA Container Toolkit；
- 尚未实现镜像签名、漏洞扫描和镜像准入；
- 网络控制目前是开关或 Docker 网络模式，尚无域名级出站白名单；
- 尚未提供多租户独立身份、配额和每租户文件系统；
- 高风险、多租户生产环境最终可演进到 Kubernetes Job，并按风险采用 gVisor、Kata Containers 或独立 GPU 节点。

## 4. 语义缓存

### 4.1 业务背景

Geo-Agent 会反复收到含义相近但表述不同的问题，例如“交并比是什么”和“解释一下 IoU”。如果每次都调用大模型，会产生重复费用和等待时间。只使用字符串缓存又只能命中完全相同的问题，覆盖率很低。

语义缓存使用 Embedding 将问题映射为向量，再通过相似度识别同义问法。但它同时会带来三类业务风险：

- **错误命中：** 两个句子相似，但用户意图或关键参数不同；
- **答案过期：** 项目代码、知识库或模型版本已经改变；
- **数据串用：** 不同项目、租户或权限范围复用了不该共享的答案。

所以第一版目标不是追求最高命中率，而是在可控范围内验证节省效果和误命中率。

### 4.2 缓存边界

| 请求类型 | 第一版策略 | 原因 |
| --- | --- | --- |
| 稳定的概念解释、方法说明、通用知识问答 | 可进行精确和语义匹配 | 答案稳定、无副作用 |
| 包含明确数字、路径、实验 ID 或硬参数的问题 | 仅允许精确匹配 | 微小差异可能改变答案 |
| 提交、取消或修改实验 | 绕过 | 有业务副作用，不能用历史回答代替执行 |
| 训练进度、任务状态、GPU 状态 | 绕过 | 依赖实时状态 |
| “这个实验”“上面的结果”等上下文相关问题 | 绕过 | 单独缓存问题会丢失会话语境 |
| 调用了工具后生成的答案 | 当前不写入 | 可能包含动态数据或权限相关结果 |

只有“模型成功返回、没有调用工具、且策略判定为稳定知识问答”的文本答案才会写入缓存。

### 4.3 端到端流程

```text
收到用户问题
  │
  ├─ 策略分类：动态请求/副作用请求/上下文问题 ─► bypass
  │
  ├─ 计算缓存作用域 scope
  ├─ 规范化文本并计算 SHA-256 ─► 精确查询
  │                                  └─ 命中
  ├─ 本地 Embedding ─► 向量相似度查询 ─► 语义命中
  │
  ├─ active 模式命中 ─► 直接返回缓存答案，并写回 Pi 会话历史
  ├─ shadow 模式命中 ─► 记录“本可命中”，但仍调用模型
  └─ 未命中 ─► 调用模型 ─► 校验无工具调用 ─► 写入 Redis
```

命中答案写回 Pi `AgentSession` 的历史记录，而不只是打印到终端。这样用户下一轮追问时，Agent 能看到先前返回的缓存答案，不会出现终端显示了一条回答、模型上下文却不知道该回答的情况。

### 4.4 三种运行模式

| 模式 | 行为 | 使用场景 |
| --- | --- | --- |
| `off` | 完全关闭 | 故障排查或紧急停用 |
| `shadow` | 查询、统计命中，但仍调用模型 | 当前推荐默认值，用于评估误命中和阈值 |
| `active` | 命中后直接返回缓存答案 | 完成离线评测和线上观察后启用 |

先 shadow、后 active 是业务风控设计。它允许团队先知道“如果开启缓存会替用户返回什么”，而不立即影响真实答案。

### 4.5 技术选型

#### Redis 作为在线缓存存储

Redis 适合存放有过期时间、需要高频读写的缓存数据，并能支持精确索引、集合、计数器和向量检索扩展。它不是事实数据库：缓存不可用时，系统仍应通过正常模型调用完成回答。

当前实现兼容两种部署：

- Redis 8 / Redis Stack 可用 Query Engine 时，自动创建 FLAT 向量索引并在 Redis 内完成查询；
- 当前 Redis 5 等不支持向量索引的环境，保留 Redis 存储，在应用内对同一作用域最多 2000 条记录做 FLAT 余弦相似度计算。

应用内 FLAT 是第一版和小规模数据的兼容方案，不适合无限增长。数据规模扩大后应升级 Redis 并使用服务端向量索引。

#### 本地 Embedding

默认采用 `Xenova/paraphrase-multilingual-MiniLM-L12-v2`：

- 支持中英文语义匹配；
- 384 维向量，存储和计算成本较低；
- 在 CPU 本地运行，不为每次缓存查询增加外部 Embedding API 费用；
- 模型文件缓存在项目的 `.geo-agent/embedding-models` 目录。

首次使用需要下载模型，因此提供单独的预热命令。在线查询有超时保护，模型未就绪时会直接绕过缓存，不阻塞正常 Agent 服务。

#### 精确键与作用域隔离

规范化后的问题使用 SHA-256 生成精确键；语义查询则使用向量相似度。缓存作用域包含：

- 租户；
- 项目；
- 意图类别；
- 语言；
- 知识版本；
- Agent 版本；
- 模型版本；
- 权限范围。

这些字段共同进入作用域哈希。不同作用域默认不互相命中，从设计上降低跨项目、跨权限和跨版本复用风险。

### 4.6 失效策略

第一版同时采用时间失效和版本失效：

- 默认 TTL 为 7 天；
- 命中时可刷新过期时间；
- 知识库、Agent、模型或权限规则变化时，通过提升对应版本使旧缓存立即失去匹配资格；
- 后续接入 RAG 和 RabbitMQ 后，可在文档发布事件中携带知识版本，驱动更精确的缓存失效。

版本隔离比逐条删除更简单、可靠；旧记录可等待 TTL 自动回收。

### 4.7 故障降级与可观测性

语义缓存采用 **fail open**：Redis 断开、Embedding 加载失败、查询超时或索引不可用时，记录错误并继续调用模型。缓存故障只能降低性能，不能导致 Agent 不可用。

当前可统计的核心指标包括：

- 精确命中数；
- 语义命中数；
- shadow 命中数；
- 未命中和策略绕过数；
- 成功写入数；
- Redis、Embedding 和查询错误数。

业务上还应重点观察：

- 缓存命中率和模型调用节省量；
- 命中后 P50/P95 响应时间；
- 误命中率；
- 过期答案率；
- 按租户、项目和问题类型拆分的命中分布。

### 4.8 当前局限

- 请求分类目前以保守规则为主，尚未使用独立意图分类模型；
- 相似度阈值需要基于真实地质问答集标定；
- 本地 Embedding 模型需要完成首次下载和预热；
- 当前小规模 Redis 部署不具备高可用能力；
- 应用内 FLAT 查询受 2000 条候选上限约束；
- 尚未接入统一租户、权限和知识发布服务；
- 不应把 Prompt Cache 与语义缓存混为一谈：前者复用模型侧重复前缀计算，后者复用完整业务答案，两者未来可以同时使用。

## 5. 关键技术选择及理由

| 技术/设计 | 选择理由 | 不承担的职责 |
| --- | --- | --- |
| Pi AgentSession + 领域工具 | 保留流式会话和工具循环，同时只向模型暴露明确的地质实验能力 | 不直接提供任意系统命令权限 |
| Worker 执行边界 | Worker 是真正启动训练进程的位置，适合做最终校验、检查点和清理 | 不负责判断知识问答是否缓存 |
| 进程沙箱 | 零额外基础设施，方便单机原型快速验收 | 不提供内核级隔离 |
| Docker 沙箱 | 文件、身份、网络和资源边界清晰，部署成本适中 | 不是绝对安全边界，也不替代镜像供应链治理 |
| Redis | 低延迟、TTL、计数与向量检索生态适合在线缓存 | 不作为任务事实状态的唯一存储 |
| 本地 MiniLM Embedding | 中英文支持、成本低、数据不出本机 | 不负责生成最终回答 |
| SHA-256 精确键 | 稳定、简单，适合完全相同问题的快速命中 | 不能识别同义问法 |
| shadow 模式 | 在不影响用户答案的前提下验证收益和风险 | 不直接节省模型调用 |
| 版本化作用域 + TTL | 同时处理业务变更和自然过期 | 不替代高风险数据的主动删除机制 |

## 7. 验收场景

### 7.1 沙箱验收

1. 合法项目、数据和输出路径可以运行训练；
2. 使用 `..` 或绝对路径访问允许目录之外时被拒绝；
3. 非白名单命令和训练入口被拒绝；
4. 训练进程中读取不到 OpenAI 等 Agent 凭证；
5. 超时后主进程、子进程或容器均被清理；
6. Docker 模式下代码和数据不可写，只有当前实验目录可写；
7. Docker 或镜像缺失时预检失败，并且不会回退为裸进程运行；
8. 检查点能够还原本次任务的沙箱模式、资源约束和失败原因。

### 7.2 语义缓存验收

1. 完全相同的稳定问题能够精确命中；
2. “IoU 是什么”和“解释交并比”等同义问题能够产生语义候选；
3. shadow 模式只记录命中，不改变模型回答；
4. 实验提交、状态和 GPU 查询始终绕过缓存；
5. 含不同 epoch、路径或实验 ID 的问题不会错误地语义复用；
6. 修改知识版本或权限作用域后不会命中旧作用域；
7. Redis 停止或 Embedding 超时时，Agent 仍能正常调用模型；
8. active 模式命中后，缓存答案能够进入 Pi 会话历史并支持后续追问。

建议准备至少 200 组地质领域样本，其中包含“应命中”和“容易混淆但不应命中”的问题对。在误命中率达到业务要求后，再从 shadow 切换为 active。

## 8. 运维命令

```powershell
# 运行当前项目测试
npm test

# 查看语义缓存状态
npm run cache:status

# 预热本地 Embedding 模型
npm run cache:warmup

# 启动 Geo-Agent
npm run geo
```

CLI 内可使用 `/cache` 查看缓存运行状态和统计信息。

## 9. 推荐演进路线

### P0：完成第一版数据验证

- 完成本地 Embedding 模型预热；
- 保持 shadow 模式收集真实问题；
- 建立 200 组以上的正负样本集，标定相似度阈值；
- 补充沙箱越界、环境变量和超时清理测试。

### P1：启用容器级实验隔离

- 安装 Docker 和 NVIDIA Container Toolkit；
- 构建固定版本训练镜像；
- 验证 GPU、只读挂载、资源限制和超时清理；
- 验收通过后将正式实验环境切换为 `docker`。

### P2：小流量启用语义缓存

- 将低风险知识问答切换为 active；
- 保留动态请求和工具回答的强制绕过；
- 建立误命中反馈、缓存禁用和版本回滚能力；
- 升级到支持向量索引的 Redis 部署。

### P3：企业级治理

- 通过 RabbitMQ 发布知识更新和缓存失效事件；
- 接入租户、RBAC、审计和资源配额；
- 增加镜像签名、漏洞扫描和准入控制；
- 多机环境使用 Kubernetes Job，并根据风险选择 gVisor、Kata 或独立节点；
- 建立统一看板，关联任务成功率、沙箱拒绝率、缓存收益和回答质量。
